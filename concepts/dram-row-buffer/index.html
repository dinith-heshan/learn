The DRAM row buffer

A strip of latches beside every DRAM array that holds one row at a time, and the reason the cost of a memory access depends on which address you touched last.

The name oversells it

Random access memory implies every address costs the same to reach. It doesn't. Two reads of the same size, nanoseconds apart, can differ by roughly threefold depending on nothing more than where the previous read landed.

The whole explanation sits in one strip of circuitry, and one awkward physical fact.

One bit, one capacitor

A DRAM cell is a transistor and a tiny capacitor. Charged is 1, empty is 0. Billions of them are etched in a grid of rows and columns. Two things follow, and the second drives everything below.

Charge leaks. It drains over milliseconds, so the controller re-reads and rewrites every row thousands of times a second just to hold the data still. That is the dynamic in DRAM.

Reading destroys. Detecting whether a capacitor holds charge drains it. There is no way to peek. Every read is also an erase.

So the chip cannot read one bit

Since sensing wrecks the cell, the chip cannot pick out a single capacitor and leave its neighbours alone. Instead it activates the entire row at once: one sense amplifier per column detects each faint charge, resolves it to a clean 1 or 0, and latches it.

Those latches are the row buffer. It holds roughly one to two kilobytes, one row's worth. Once loaded, it is the only intact copy of that data anywhere on the chip.

The buffer is built from cross-coupled transistors, the same static circuits used in SRAM, not from more capacitors. That is not a preference. If the buffer were capacitors, loading it or reading it would destroy the data again and the problem would move up one level. A DRAM chip is physically a hybrid: a dense capacitor array with a thin SRAM-like strip along its edge.

Then reads are cheap, until they are not

With a row latched, the column decoder pulls the requested bits straight out of the buffer. Nothing touches the cell array. Ask for another column in the same row and you pay only this step again.

That is a page hit, "page" being the industry's name for whichever row currently sits in the buffer.

The bill comes when you leave the row

The original capacitors were drained during activation. Before a different row can open, the buffer's contents must be written back into them. That restore is called precharge, and it is the cost nobody expects.

So a page miss is three operations where a hit was one: precharge the open row, activate the new one, then read the column.

How confident is this The three-phase structure is how DRAM genuinely works and is defined in the JEDEC standards. The numbers are one common DDR4-3200 CL22-22-22 module, where the three timings happen to be equal, making a miss almost exactly three hits. That symmetry belongs to this particular part, not to DRAM in general. Other kits and DDR5 shift the ratio, and a real access also carries controller queueing and bus time this diagram leaves out.

Which addresses land in the same row

A physical address is a plain binary number, but the controller never uses it whole. It slices it into fields, each routing to different hardware.

Row bits sit at the high end, column bits at the low end. Drag by ones and the column field churns while the row field sits still. Sequential access keeps landing in the open page by construction, not by luck.

Random access does the opposite. Jump unpredictably and the row field changes almost every time, so nearly every read pays the full three phases.

Why one buffer would be unbearable

A chip is not one grid. It is carved into independent banks, typically eight to sixteen, each with its own array and its own row buffer. Different rows can be open in different banks at the same time.

This is what makes the arrangement survivable. With a single buffer, every miss would stall on the full restore-then-activate sequence with nothing else able to proceed. With banks, the controller reads from one while activating another and overlaps the expensive part instead of waiting through it.

Real systems stack more on top: multiple ranks per channel, multiple channels per socket. Memory bandwidth scales with channel count because it is not one pipe getting wider, it is more buffers kept busy at once.

Three things it is not

The row buffer is a DRAM cache

It is not, and "DRAM cache" already means something else: fast DRAM placed in front of a slower memory tier and used as a genuine cache with its own eviction policy. The row buffer makes no decisions. It holds whichever row was opened last and loses it the moment another row in that bank is needed. No policy, no choice, no retention.

A DRAM page is an OS page

Unrelated concepts wearing the same word. A DRAM page is the row currently in the buffer, one to two kilobytes, a property of the chip. An OS page is a unit of virtual address space, typically four kilobytes, a property of the kernel and MMU. Neither implies the other.

Registers are the top of the cache hierarchy

Registers are a separate tier above L1, not the smallest cache. The distinction is who decides: cache contents are chosen by hardware guessing what comes next, while registers are assigned explicitly by the compiler or JIT. Collapsing them into one box hides that difference, which is the interesting part.

What this changes downstream

Locality is not a software convention. It is a physical property of the address, and the same principle repeats at three distances from the CPU: cache lines, row buffers, disk blocks. Contiguous access wins at every one of them for structurally the same reason.

That is the mechanism under a set of rules usually taught as folklore. Columnar layouts like Arrow and Parquet keep scans contiguous. Broadcasting a small table avoids a shuffle. Hash joins and pointer chasing through row objects are the pathological case, forcing an activation on nearly every probe.

Model, not mechanism Treating a Spark shuffle as "random access, scaled up" is a useful analogy and nothing more. Shuffle cost is dominated by network and serialisation, not DRAM timings. The shared idea is that unpredictable access defeats prefetching and batching at every layer. The hardware is not literally what is slow when a job spills.

Recall

Reading a DRAM cell destroys its charge. Work forward from that one fact and derive why leaving a row costs more than staying in it.

If sensing drains the cell, the buffer holds the only surviving copy after activation. The array itself is now blank for that row. So the chip cannot simply abandon it and open another, because the data would be gone. It must write the buffer back into the capacitors first.

That restore is precharge. Staying in the row costs one column read. Leaving costs a restore, an activation, and then the column read.

Why can the row buffer not be built from the same capacitor cells as the array it serves?

Because it would inherit the exact problem it exists to solve. Loading capacitors requires sensing them, and reading them again would destroy them again, so you would need a second buffer to hold the first buffer's contents, and so on.

Latches break the regress: they hold a stable electrical state, survive unlimited reads, and never need refreshing. The cost is density, which is why the buffer is one row wide rather than a second array.

Suppose row bits sat at the low-order end of the address and column bits at the high end. What happens to a sequential scan, and why?

It inverts to worst case. Incrementing the address would step the row field on every access while the column field stayed put, so consecutive addresses would land in different rows. Every read becomes a page miss.

The real ordering is chosen precisely to avoid that. Sequential access exhausts all columns in a row before crossing into the next one, which is why "sequential is fast" is arranged by the controller rather than being an accident.

Someone describes the row buffer as a small cache in front of the DRAM array. Where exactly does that analogy fail?

A cache retains data across accesses according to a policy, decides what to evict, and holds unrelated items at once. The row buffer does none of that. It holds exactly one row, chosen by whichever address arrived last, and loses it unconditionally when another row in that bank is requested.

It is also not optional. A cache is an optimisation you could remove; the buffer is structurally required because reads are destructive. Separately, "DRAM cache" is already taken as a term for fast DRAM fronting a slower tier, so the analogy collides with real vocabulary.

Reconstruct the argument for why chips carry 8 to 16 banks rather than one large array with one buffer.

With a single buffer, only one row can be open per chip, so every miss serialises: restore, activate, read, with the entire chip idle throughout. Latency would be exposed in full on every row change.

Independent banks each have their own array and buffer, so the controller can activate a row in one while reading from another, hiding the slow phase behind useful work. The gain is throughput through overlap rather than any single access getting faster.

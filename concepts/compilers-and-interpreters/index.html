Compilers and interpreters

A compiler turns a program into another program; an interpreter takes a program and its data and produces the program's output. Everything else is a question of where you stop and when.

The gap

A CPU does one thing in a loop: fetch a number from memory, decode it as an instruction, do it, move on. Those numbers are the only language it speaks. A file containing return a + b is, to a CPU, just ASCII bytes — no more executable than a photograph.

So something has to bridge that. There are two strategies, and every system is one of them or a stack of both.

  • Translate ahead of time. Read the source, work out which machine instructions have that effect, write them to a new file. You now have a second artifact you can run forever without looking at the source again.
  • Don't translate — just do what it says. Write a program that reads the source, works out what the first step means, performs it, and moves on. The source is never converted. It is consulted, repeatedly, while the work happens.

Stated exactly, which settles most arguments about this topic:

compiler(source)          → another program
interpreter(source, data) → the program's output

Look at what is on each side. A compiler never sees your program's data. It finishes and exits before your program starts. An interpreter needs the data, because it is the thing doing the running.

The category error

"Python is an interpreted language, C is a compiled language" is wrong as stated, and believing it blocks everything that follows.

Compiled and interpreted are properties of an implementation, not of a language. A language definition says what programs mean. It says nothing about how you get a machine to produce that meaning. Cling is an interpreter for C++. GraalVM compiles Java ahead of time to a native binary. V8 compiles JavaScript — the canonical "scripting language" — to optimised machine code in every browser you have ever used.

The answerable question is never "is X compiled?" but "what does this implementation do, and when does it do it?" The panel on this page answers exactly that for eight of them.

The numbered list

Imagine driving the same route a thousand times with directions written as prose: "out of the car park, and at the roundabout — the second one, not the little one — take the exit toward the retail park." Every trip you must untangle what that means. Now rewrite it once as a numbered list of single unambiguous actions. Same route, none of the untangling.

Model vs mechanism. The route analogy is a mental model. What follows is not — Python literally does this, and the list is a file you can find on disk.

Python untangles s = s + x exactly once, when it loads your file, into four dumb steps:

LOAD_FAST    1 (s)      get the value of s
LOAD_FAST    2 (x)      get the value of x
BINARY_OP    0 (+)      add the last two things
STORE_FAST   1 (s)      put the answer back in s

In a loop, the body appears once, with a JUMP_BACKWARD at the end. A million iterations untangle the source once and run the list a million times. The text is never consulted again — it is not even kept.

That list is bytecode. Each step is stored as a small number rather than a word, and small numbers fit in a byte. LOAD_FAST is stored as 124; the name only exists because you asked for a readable printout.

You can prove the source is genuinely unnecessary. Compile a file with python -m py_compile, delete the .py entirely, then run what is left:

$ python3 __pycache__/greet.cpython-311.pyc
DINITH!

Which forces a correction to the tidy two-way split above. Turning source text into that list is turning a program into a different program — no data in sight. That step is compilation. Python has a compiler in it, and __pycache__ is where it saves the results. What differs from C is not whether Python compiles but how far: C goes all the way to instructions the CPU executes; Python stops at a list something else must read.

You accidentally built a computer

Someone decided which steps that list is allowed to contain — LOAD_FAST, BINARY_OP, JUMP_BACKWARD, a couple of hundred in all. A fixed menu of operations a machine can perform is an instruction set, and every computer has one. Intel decided x86's decades ago.

So Python has an instruction set, somewhere to keep values, and a pointer tracking which step it is on. It has a computer. The only difference from Intel's is what it is made of: Intel's is etched into silicon, Python's is a program reading numbers off a list. That is what virtual machine means here.

Not that kind of VM. VirtualBox and VMware imitate a real machine, convincingly enough that a real OS installs on it. A language VM imitates a machine nobody built and nobody will — invented on purpose to be a convenient target.

Java's is the famous one. static int add(int a, int b) compiles to four one-byte instructions in a .class file:

iload_0   get local 0        (0x1a)
iload_1   get local 1        (0x1b)
iadd      add the last two   (0x60)
ireturn   return the answer  (0xac)

Different names, different decade, identical idea. The number identifying the operation — 124, 0x60, or x86's 0x8d for lea — is an opcode; the bytes describing what it acts on are operands. There is no conceptual difference between a bytecode opcode and a machine-code one. The difference is entirely who decodes it: a software loop looking up a table, or a circuit routing signals.

Three things follow, and they are why the design is everywhere. Your compiler only has to know one machine, so porting to new hardware means porting the VM once. You can invent instructions no chip would provide — Intel will never ship "call this method, working out at runtime which class's version to use", but the JVM has invokevirtual. And other languages can move in: Kotlin, Scala and Clojure exist because the JVM did, which is also why Spark is written in Scala.

Why dynamic languages are slow

The usual explanation is "there's an interpreter loop in the way." It is the smaller half. Here is an experiment that splits the cost apart — summing five million integers three ways.

sum of 5,000,000 integers
Python loop98.3 ms
built-in sum()28.3 ms
numpy .sum()3.0 ms
Measured once in a single Linux container. Treat the ratios as indicative, not as a benchmark.

The middle bar is the interesting one. sum() is a C function inside CPython — while it runs there is no bytecode, no dispatch, no interpreter at all. So the gap from the first bar to the second is exactly what the interpreter costs: 3.5x.

If the loop were the main problem, the second and third bars would be close. Both are C; neither interprets anything. numpy is another 9.5x faster. Most of Python's slowness lives somewhere the interpreter is not.

It lives in what a actually is. Not a number — a pointer to an object on the heap. Step through what a + b has to accomplish:

What a + b costs

step 1 of 11
    In C, all of it is lea (%rdi,%rsi,1),%eax — one instruction.

    One step is the work. The rest is ceremony, and it happens on every single execution. The same point as a measurement: sys.getsizeof(1) is 28 bytes, because the number 1 is an object with a type pointer, a reference count and a length field. An int64 in numpy is 8. Five million of them: about 180 MB of pointers and scattered objects, against numpy's 40 MB of contiguous values.

    Why Python has to do this. In def add(a, b): return a + b, what are a and b? You cannot answer and neither can the compiler — integers, strings, arrays, a class with __add__, all legal. C knows because you wrote int. That single fact is what buys the one-instruction version. A language that refuses to commit to types until runtime must box every value with its type and consult the box on every operation.

    This is why numpy, pandas, Arrow and Parquet exist. A pandas column is not a list of Python objects; it is one contiguous block of raw values with the type recorded once for the whole column. "Vectorise it, don't loop" means: hand the whole column to code that already knows the type, so the per-value ceremony happens zero times instead of five million.

    CPython has since learned to watch. Run two identical functions a thousand times each, one on integers and one on strings, then look at their bytecode:

    before any runs:      BINARY_OP
1000 runs on ints:    BINARY_OP_ADD_INT
1000 runs on strings: BINARY_OP_ADD_UNICODE

    Same source. The bytecode rewrote itself, differently, based on what actually flowed through it, with a cheap guard that reverts if the assumption breaks. This is information a compiler could never have had — no static analysis proves add only ever gets integers, but running it a thousand times does.

    Watch, guess, guard, undo

    Specialising is a half-step. The full step: once you know the types, generate real machine code — what an ahead-of-time compiler would have emitted if only you had declared them. But you observed the types rather than proving them, and observations can turn out wrong.

    So a JIT first waits. Most functions run a handful of times and compiling them is pure waste, so it counts, and invests only in the ones that earn it. Here is V8 making that call:

    [marking <JSFunction add> for optimization to TURBOFAN,
 reason: hot and stable]
[completed compiling <JSFunction add> - took 0.75, 22.05, 0.09 ms]

    Called a lot, and the types have stopped changing — both conditions. Twenty-two milliseconds spent compiling one two-line function. The return, timing the identical 300,000 calls over and over:

    300,000 calls to the same function, round by round
    round 17.69 ms
    round 20.53 ms
    round 40.36 ms
    Same code, same inputs, nothing changed in the source. Round one ran interpreted.

    The compiled version has integer addition baked in, so it opens with a guard — two or three instructions checking the assumption still holds. When one fails:

    [bailout (kind: deopt-eager, reason: not a Smi):
 deoptimizing <JSFunction add>, <Code TURBOFAN>, bytecode offset 2]

    Smi is V8's small integer stored directly rather than as a heap object; the guard tripped on a string. Deoptimisation is the hard engineering in any JIT: you are mid-execution inside optimised machine code, values in registers in a layout the interpreter knows nothing about, and you must rebuild the interpreter's state exactly as it would have been and resume at the right step, as though the optimised version never existed.

    That escape hatch is the entire point, because it lets a JIT bet on facts that are true in practice but not provable: this list only ever held integers; this method is never overridden, so inline it; this branch is never taken. An ahead-of-time compiler must emit code correct for every legal execution. A JIT only needs code correct for the execution actually happening. That is a far weaker requirement, and it is why JIT-compiled JavaScript sometimes beats compiled code written in a much better language.

    The bill is that 7.69 ms first round — warm-up. It is why a fresh JVM service is sluggish for a minute, why serverless cold starts hurt, and why a short script sees no benefit at all: it exits before anything gets hot.

    Where everything sits

    Two questions place any system: when does translation happen relative to running, and how far down does it go. Nothing occupies a single point — every real system is a path, which is what the panel draws. TypeScript is the one worth staring at: three translations at two different times, the middle one a language you could have written by hand.

    Notice what tsc actually does — it deletes the types. They checked your work at build time and then evaporated; nothing downstream ever learns that name is a string. Which is why TypeScript buys you zero runtime speed, while int in C is precisely what buys the one-instruction add. Same-looking annotation, opposite consequence, because of which stage consumes it.

    The categories leak in both directions, which is the real lesson:

    • Profile-guided optimisation is ahead-of-time stealing the JIT's trick. Compile with instrumentation, run on sample input, record which branches went where, recompile using that. On a C program whose function pointer is the same function 99.9999% of the time: 0.42 s → 0.22 s. Its weakness is obvious — the profile came from your sample run, not production.
    • GraalVM Native Image goes the other way, compiling Java to a standalone binary. Startup drops to milliseconds; peak throughput on a long-running server is typically worse than a warmed JVM, because everything the JIT was doing is gone.
    • Android's ART refuses to choose: interpret, JIT the hot methods, then ahead-of-time compile them from the collected profile while the phone charges.

    There are also two kinds of JIT. A method JIT compiles a whole function (HotSpot, V8, .NET). A tracing JIT compiles a hot path: record the exact sequence one loop iteration performs, straight through calls and branches, and compile that straight line, with every road not taken becoming a guard. Inlining comes free and the result is perfectly linear code. It is superb on tight numeric loops and shaky on branchy logic — PyPy and LuaJIT use it; Firefox tried it and went back to a method JIT.

    Honest numbers on CPython's own JIT. It has been in CPython since 3.13 and, as of 3.15, is built into official binaries but still off by default — you opt in with PYTHON_JIT=1. Measured gain is roughly 4–12% depending on platform, per PEP 836, against V8's 19x. The reason is the section above: a JIT bolted onto an existing interpreter can remove the dispatch, but it cannot make a Python integer stop being a 28-byte heap object. That is baked into the object model and every extension ever written. Which is also why "just compile my Python ahead of time" does not get you C speed — the compiler still does not know the types.

    Your query engine is this same story

    SQL is a language and your database implements it. The parse produces a tree, the optimiser rewrites it, and the physical plan is a tree of operators — Scan, Filter, HashJoin, Aggregate — which is a program in an instruction set of relational operations. So plan(SQL) → physical plan is a compiler and execute(plan, data) → rows is an interpreter, by the definition at the top. EXPLAIN is a disassembler.

    With one thing no language compiler has: statistics about the data. gcc has no idea whether your loop runs three times or three billion. A database estimates how many rows reach each operator before running anything. That is why join order matters, and why stale statistics produce catastrophic plans — a compiler with a crystal ball, only as good as your last ANALYZE.

    Execution then went through the exact evolution above:

    • The iterator model — every operator exposes next(), returning one row, pulled up through the tree. This is a tree-walking interpreter, with the same costs: one indirect call per operator per row, boxed tuples throughout.
    • Vectorised execution — pass a batch instead (DuckDB uses 2048 rows). Dispatch amortises to nothing and the inner loop runs over one column's contiguous memory. This is the numpy answer, applied to a database. DuckDB, ClickHouse, Velox and Photon all work this way.
    • Query compilation — generate code for this specific query and compile it, collapsing the whole tree into one fused loop. Spark's whole-stage codegen emits Java source at runtime, compiles it with Janino, and the JVM then JITs that — three stacked translations, two while your job runs. The *(1) markers in explain() output mark the fused stages.
    SELECT sum(v) FROM t WHERE c = 1 — over 20,000,000 rows
    Python row loop559.4 ms
    pandas124.8 ms
    DuckDB29.9 ms
    Same rows, same answer. The last gap is mostly DuckDB fusing filter and sum into one pass where pandas materialises an intermediate.

    And the trade-off is identical, tiers included. Postgres decides per query, using estimated cost rather than observed call counts:

    jit                       on
jit_above_cost            100000   → compile at all
jit_inline_above_cost     500000   → also inline
jit_optimize_above_cost   500000   → also optimise hard

    That is the JVM's interpreter → C1 → C2 ladder, rebuilt in a database. Its failure mode is the mirror image too: a bad estimate compiles a query that turns out tiny, and you pay for nothing.

    Three things this should change in practice. "Vectorise it" is not a pandas idiom — it is the same instruction as "get out of the interpreter loop" and "unbox the values", wearing a third hat. A Python UDF in Spark is a hole in the fused loop: Spark cannot generate Java for code it cannot see, so the pipeline stops, serialises rows, ships them to a Python process and boxes them — every optimisation above switched off for the duration, which is why Arrow-based pandas UDFs help and a clumsy native expression still beats an elegant UDF. And stale statistics are a database's version of a JIT that will not stop deoptimising: in both cases the system bet on how the data would behave and lost.

    Python compiles your code. What does it compile it to, and why doesn't that make it fast?

    To bytecode — a flat numbered list of simple steps, saved in __pycache__ as a .pyc you can run after deleting the source. That is compilation by the definition at the top: program in, different program out, no data involved.

    It doesn't make it fast because the translation stops short of machine code, and more importantly because it changes nothing about how values are stored. BINARY_OP + still has to follow two pointers, read two type fields, look up the right addition, unpack the values, allocate a new 28-byte object for the result and adjust reference counts. Removing the interpreter loop entirely buys about 3.5x. Removing the boxing buys another 9.5x.

    A new language is described as "AOT compiled". What does that tell you about startup and peak speed, and what can it never do that a JIT can?

    Startup is instant and speed is flat — no warm-up, because all the work finished before the process began. That makes it right for short-lived things: CLI tools, serverless functions, anything that exits before a JIT would pay for itself.

    What it can never do is bet on facts that are true but unprovable. An AOT compiler must emit code correct for every legal execution, so it keeps the indirect call in case a subclass overrides the method, and keeps the type checks in case a string shows up. A JIT only needs code correct for the execution actually happening, plus a guard and a way back — so it can inline the method it can see and assume the integers it has been getting.

    Profile-guided optimisation is the partial exception: an AOT compiler making the same bet from a recorded earlier run, roughly 2x on branch-heavy code, limited by whether that recording resembles production.

    V8 compiled a function assuming both arguments are integers. Tomorrow someone passes a string. Walk through what has to happen.

    The compiled code opens with a guard — a two-or-three-instruction check that both arguments are still small integers. The string fails it, and the runtime bails out.

    Deoptimisation is then the hard part. Execution is partway through optimised machine code, with values held in registers in a layout the interpreter has never heard of. The runtime must reconstruct the interpreter's state exactly as it would have been at that bytecode offset — rebuild the frame, unbake the assumptions, box values back into objects — and resume interpreting at the right step, as though the optimised version had never existed.

    Then it starts watching again. If the function goes back to being hot and stable, it gets recompiled, in under a millisecond.

    TypeScript declares name: string. C declares int a. Both are type annotations. Why does one make the program faster and the other not?

    Because of which stage consumes the annotation. tsc checks it at build time and then deletes it — the emitted JavaScript is the same code with the types stripped out. Nothing downstream, not V8 and not the CPU, ever learns that name is a string, so nothing downstream can act on it.

    C's int survives into code generation. It is exactly what lets the compiler decide the value is four bytes in a register and emit a single machine instruction instead of the eleven-step ceremony Python performs.

    The general shape: an annotation only buys speed if it reaches the stage that generates code. This is also why AOT-compiling Python doesn't give you C speed — there are no types to reach that stage.

    A Spark job with a Python UDF is far slower than the same logic in native expressions. Why, structurally?

    Spark's whole-stage code generation fuses a chain of operators into one generated Java loop, which the JVM then JITs. A Python UDF is a hole in that loop: Spark cannot generate Java for code it cannot see.

    So the pipeline has to stop at the UDF, serialise rows, ship them to a separate Python process, box each value into a Python object, run the function, and bring the results back. Every optimisation in this page is switched off for that stretch — no fusion, no JIT, full boxing, plus inter-process transfer.

    Arrow-based pandas UDFs help because they at least move columnar batches instead of row-at-a-time objects, but the process boundary remains. An awkward native expression usually beats an elegant UDF.
